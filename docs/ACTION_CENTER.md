# Action Center

Open `/dashboard/actions` to review actual business-owned invoice queues. The page uses the existing charcoal/lime theme, with queue cards, a sortable table and a payment-action card beneath the selected invoice. The Filter invoices component has been removed at the owner's request. The landing page and financial authorization rules are preserved.

- Queue cards show business-wide totals. Approval, hold and scheduled counts use current-version decisions on OPEN obligations. Rejected totals use REJECTED status. All open actions is the sum of the three open queues and excludes rejected records and PAY_NOW/settled/processing records. These are decision queues; command eligibility is checked separately.
- Choose a card to switch queues. The table retains server sorting and pagination; Refresh in the results header reloads business totals and the current queue. The Action Center has no search or decision-filter form. The separate Invoices inbox retains its existing search.
- Sorting happens in PostgreSQL before pagination: due date ascending/descending, amount ascending/descending, or received date descending. Null due dates/amounts sort last; IDs break ties deterministically. Amount sorting uses exact PostgreSQL numerics.
- The table fetches 25 owned rows per page. Selecting a radio button shows one invoice's payment card from the actual detail API; changing queue/page/selection removes the previous card and its confirmation. There is no bulk approval.
- The card displays the actual invoice identity/vendor, nominal amount, due date and current recorded decision. Guidance uses stored reasons. Missing details/offers and failed requests remain explicit; unavailable totals are never replaced by zeros or sample rows.
- Approve exact terms is enabled only for a currently loaded OPEN invoice with a REQUIRE_APPROVAL decision and an available exact offer, without an active payment. Clicking it refreshes the detail before showing a frozen confirmation snapshot of payout, recipient, chain/token, invoice/policy/vendor/PO versions and expiry. A reason and explicit confirmation are required. The server still validates the offer hash/version and all eligibility rules. A verified discount can make the exact payout differ from the nominal invoice amount.
- Reject and Re-evaluate also refresh the detail before opening a reasoned confirmation. They call the existing version-bound services; command UUIDs are stable for identical payload retries. Re-evaluation can invalidate safe unsubmitted authorization/reservations; rejection cannot reverse a submitted transfer.
- SUBMITTING, PENDING, UNKNOWN, SETTLED and rejected invoices have disabled card actions. Safe unsubmitted RESERVED intents retain the existing server-controlled rejection/re-evaluation cancellation path. Pending or unknown payments require the full invoice/payment reconciliation workflow; no resend is added.
- While a card command is pending, Close and Escape cannot dismiss its confirmation. Errors remain visible in the dialog; no automatic financial retry occurs. Successful commands refresh the queue and card. The existing background worker decides whether an approved invoice can proceed under configured dispatch settings; the card does not bypass it or directly submit a transfer.
- Full invoice review remains available for source evidence, corrections, treasury evidence, payment state and audit export. Reviewer access remains blocked by the shared workspace role gate.

The disposable PostgreSQL-backed browser journey exercises card cancellation/no payment, required reasons, actual exact approval, re-evaluation, rejection and disabled rejected states, followed by synthetic settlement/export and scheduled worker restart checks. Transfers use isolated synthetic adapters and do not establish live Circle/Arc settlement acceptance.

Payment outcomes take priority over historical decision guidance. An UNKNOWN attempt displays that approval was recorded but payment is unresolved, keeps all financial actions disabled, and links to its invoice evidence. Future Circle submission errors retain only a bounded HTTP status, numeric provider code, submission stage and correlation UUID; raw SDK messages, credentials and request bodies are not exposed.

For the owner-reported 16 October rejection, Circle returned HTTP 400/code 2 because neither tokenId nor blockchain was supplied. The adapter now verifies the configured wallet ID/address, then submits using walletAddress + ARC-TESTNET + the fixed USDC token address. The original immutable amount, recipient, fee cap and provider idempotency key remain authoritative. The installed SDK's walletId branch disallows an explicit blockchain, so these two wallet identification forms are not combined.

Trusted offline recovery in `apps/server/src/payments/rejected-submission.ts` is deliberately absent from public HTTP routes and automatic dispatch. It accepts only the specific human-reviewed missing-token-identification rejection, matches the original key/time/business/terms, requires UNKNOWN without a provider ID/hash, and atomically records FAILED with rejection evidence, releases the reservation, advances the invoice version and appends an audit event. Original approvals/decisions remain historical and cannot authorize the new version. Empty history, timeouts or a bare HTTP error never authorize this recovery. Ordinary pending/on-chain outcomes still use independent receipt reconciliation.

Treasury accounting treats an audited validation rejection separately from an on-chain failure: it contributes no network fee, expenditure or active hold. This exception requires the matching owned rejection event and no provider ID/state/hash/receipt. Uncertain failures and receipt-bearing transactions retain the existing evidence requirements.
